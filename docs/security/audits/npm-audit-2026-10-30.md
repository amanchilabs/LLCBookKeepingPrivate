## Finding 1 — deepmerge prototype poisoning

- Advisory: [GHSA-gcqx-w48m-w2h4](https://github.com/advisories/GHSA-gcqx-w48m-w2h4), CVE-2026-93753.
- Installed: `deepmerge@4.3.1`.
- Affected: `>=4.2.0 <=4.3.1`. Advisory lists no patched version.
- Full dependency paths:
  - `llc-bookkeeping-private -> expo@58.0.21 -> @expo/config@58.0.9 -> deepmerge@4.3.1`.
  - Expo CLI, Metro config, prebuild config, and local-build-cache packages resolve the same `@expo/config@58.0.9` node; npm reports them as affected parents.
- Relevance: build/development configuration processing. `@expo/config` calls `deepmerge` while merging Expo configuration modifications and plugin properties. The app's Metro financial UI bundle does not import `deepmerge` or `@expo/config`.
- Reachability and inputs: the vulnerable merge operation is reachable when Expo tooling processes project configuration. The data must be a crafted source object containing keys that poison a target prototype. Candidate inputs are local Expo config values and plugin-provided configuration objects. This repository's app config is developer-controlled code; Expo plugins are also installed build dependencies. No transaction, CSV, receipt, backup, or runtime network value is passed to `deepmerge` by this app.
- Exploit conditions: an attacker must influence a config object that is merged while a developer/build tool runs, or compromise an installed plugin/build dependency. This is not a remotely reachable financial-record operation in the shipped app. The vulnerable call is reachable in the development/build process; it is not claimed unreachable.
- Compatible remediation: none published in the installed dependency line. Expo SDK 58.0.21 is the current `latest` stable and its supported `@expo/config@58.0.9` requests `deepmerge ^4.3.1`; npm registry currently has no later deepmerge release. Replacing it with an unreviewed fork, hand-edited node_modules, or npm override would not be an upstream-compatible fix and was not done. Reassess when Expo or deepmerge publishes a compatible fix; alternatively test a maintained Expo fork that removes or safely wraps the merge path.
- Uncertainty: no exploit was run against Expo's config merge. The exact impact depends on whether untrusted config objects can enter a build; package advisory describes inherited unintended values in returned objects. The Expo parent-package advisories are propagation.

## Finding 2 — Zod array-validation memory exhaustion

- Advisory: [GHSA-mrhx-c7xc-m3w5](https://github.com/advisories/GHSA-mrhx-c7xc-m3w5), CVE-2023-54404.
- Installed: `zod@3.25.76`.
- Affected: `<4.6.6`; patched: `4.6.6`.
- Full dependency path: `llc-bookkeeping-private -> expo@58.0.21 -> @expo/cli@58.1.17 -> zod@3.25.76`.
- Relevance: Expo CLI development tooling. The inspected consumers are `DevToolsPluginCliExtensionResults.parseOutputText()` calling `DevToolsPluginOutputSchema.safeParse(JSON.parse(txt))`, and Expo CLI's dev-tools extension schema helpers. `zod` is not imported by application code or the native production financial workflow.
- Reachability and inputs: the vulnerable array validator is reachable when the development server parses JSON output from a registered DevTools plugin. The attacker-controlled input would be plugin output with a very large array containing invalid entries, causing the validator to allocate many issue objects. The CLI caps output only at V8's maximum string length, which is not a practical low bound for memory exhaustion. Triggering this requires a development server plus a plugin or other party able to supply that output; the app has no remote AI, backend, or plugin execution path in production.
- Compatible remediation: Zod 4.6.6 fixes the advisory, but Expo CLI 58.1.17 declares `zod ^3.25.76`; substituting Zod 4 violates the declared dependency range and has not been shown compatible by Expo. No current later CLI 58 version is published. A scoped override was not applied because it would be unsupported and could break dev-server schemas. A compatible Expo CLI release or a reviewed local patch with regression tests is required.
- Uncertainty: the app does not register a third-party DevTools plugin; however Expo CLI has the parser code and may expose it through dev tools. No malicious plugin-output test was run. The per-package npm audit labels propagate high severity to Expo/CLI; they do not mean a production app request can reach this parser.

## Remediation decision and risk status

No safe compatible dependency update exists in the installed SDK 58 line at this snapshot. Findings remain open; this report does not accept risk for release. Before a real-data workflow or release, re-run the audit and either adopt Expo-supported patched packages, obtain an upstream fix, or complete a separately reviewed and regression-tested dependency patch. Do not apply the offered Expo 51 downgrade.
